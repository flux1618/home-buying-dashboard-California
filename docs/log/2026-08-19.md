# 2026-08-19 — From a page with a calculator to a system with an engine

**Commits:** `f136262` … `7634f07` (14)
**Volume:** ~11,400 lines added across 76 files — ~7,900 Python, ~1,600 documentation
**Tests at end of day:** 407 offline, passing in ~1.2s; 6 live tests deselected by default
**ADRs written:** 0001–0008

## Where the day started

A single static page: `index.html`, `app.js`, and a `data.json` of market data. It looked
finished. It modeled affordability, rent-versus-buy, submarket scores, and had a property
scorer where you typed in a few facts and got a 0–100 number back.

The problem with it was not visible on the screen. Every rule it applied was hand-written into
JavaScript, every threshold was a literal, and nothing in it could look anything up. It was a
report that resembled a tool.

The goal for the day was to build the thing the page was pretending to be, without breaking the
part that already worked.

## What got built

### An engine with nothing in it

`analyzer/core/` is pure Python — no framework, no network, no I/O. That is
[ADR 0002](../adr/0002-pure-scoring-core.md), and it is enforced two ways: a test that reads the
source with `ast` and bans the imports, and a CI job that installs the package with **no extras
at all** and runs a full analysis on an interpreter where `fastapi`, `pydantic`, and `httpx` do
not exist. The first check can be fooled by a dependency that becomes load-bearing without
appearing in an import line. The second cannot.

The buyer's constraints live in `buyer_profile.toml`, not in code. Adding a persona — a hospital
employee, a remote engineer, a school-focused family — means copying a file, not editing a
function. That was the single most useful structural decision of the day, and everything later
in this entry depends on it.

### Six source stations, one failure contract

`analyzer/sources/` — geocoding, parcel, flood, commute, broadband, and the shared HTTP layer.
Each obeys the same contract from [ADR 0006](../adr/0006-source-station-contract.md): **never
raise, never guess.** A station returns data or it returns a documented degraded state. It does
not substitute a plausible number.

That contract earns its keep immediately, because two of the six are degraded on any given day:

| Source | State | Why |
|---|---|---|
| Census geocoder | Working | — |
| FEMA NFHL flood layer | Working | — |
| OSRM routing | Working | — |
| Nominatim | Working, throttled to 1.1s | Usage policy |
| Spartanburg County parcel data | **Mirror from Feb 2021** | The county's live server has a broken TLS certificate chain |
| FCC broadband map | **Unavailable** | Returns 401 without an API key |

On the parcel server: the fix that would have "worked" was disabling certificate verification.
That was rejected. A stale-but-honest mirror with a documented date is a better artifact than
fresh data obtained by turning off a security check, and the report labels every parcel figure
with its vintage.

### Three doors, one engine

A CLI for one address, a batch runner for a CSV shortlist, and a localhost-only FastAPI service
in a container. All three call the same core, which is
[ADR 0007](../adr/0007-http-service-container-and-split-ci.md).

The temptation here is to let each door grow the little helper functions it needs. That is
precisely how a codebase ends up with two implementations of the same scoring that agree on
Tuesday and disagree by Friday. Instead the shared functions were refactored so the door is
genuinely thin: `read_shortlist(path)` wraps `parse_shortlist_text(text)`, `write_summary_csv`
wraps `write_summary_stream(result, handle)`, `write_markdown` wraps `render_markdown(result)`.
The API streams; the CLI writes files; neither owns any logic.

There is a test class called `TestDoorsAgree` that compares HTTP response bodies line-for-line
against the CLI's output files. It exists because "they share a core" is a claim, and claims
should be executable.

### A container that means it

Two-stage build, `python:3.12-slim`, non-root uid 10001, multi-arch for amd64 and arm64 so it
runs on the Pi cluster, BuildKit cache keyed by `TARGETARCH`, healthcheck on `/health`. Compose
binds to `127.0.0.1:8000` only, mounts the profile read-only, and caps memory at 512M.

The service is deliberately unauthenticated, which is exactly why it is bound to localhost. That
is a documented decision, not an oversight — see
[KNOWN_LIMITATIONS](../KNOWN_LIMITATIONS.md).

### CI split by what a failure means

Two workflows, and the split is the whole point:

- `tests.yml` runs on every push and contains only what can be verified without depending on
  someone else's server being up. It must be boring. A workflow that goes red because
  Spartanburg County had a bad afternoon teaches people to ignore red builds, and then it stops
  protecting anything.
- `live.yml` runs nightly against the real endpoints, with no retries and no exact-score
  assertions. A failure there means "a source changed, go look" — so it opens or comments on a
  single `source-drift` issue rather than blocking a commit.

The live workflow was run manually to confirm it works end to end: 6 live tests passed and a
full analysis returned `WATCH 52`, matching the local run exactly.

## The bugs

None of these were typos. Each one is a category of mistake worth recognising again later.

### Silence scored as perfection

Two properties with no county parcel record scored a clean **100 TAKE** and outranked a
fully-documented house at 52.

Every deduction was guarded by "if we know this value." Not knowing anything therefore cost
nothing, and the engine rewarded absence of evidence with a perfect score. It was confidently
recommending the two houses it knew the least about.

The fix is an explicit `unknown_facts` list that caps the score below the TAKE threshold, and
the cap is **one-directional** — it can only lower a score, never raise one, so a missing data
source can never make a property look better than it is. The report says which fact was missing
and that the cap applied.

This is the most valuable bug of the day because the code was doing exactly what it said. The
error was in the design: treating "no data" and "no problem" as the same thing.
[ADR 0005](../adr/0005-capital-expenses-deduct-and-unknowns-pin.md) records the rule.

### A default argument froze the world at import time

`analyse_shortlist(runner=run)` bound the network function as a **default parameter**, which
evaluates once at import. Tests that believed they were substituting a fake runner were making
real Census requests — and passing, which is the worst possible outcome. A test that passes for
the wrong reason is more dangerous than one that fails.

Fixed with late binding: default to `None`, resolve inside the call.

### The rulebook walked into site-packages

`load_profile()` located `buyer_profile.toml` by walking up from its own source file. That works
perfectly from a checkout and breaks the instant the package is installed, because the walk then
starts inside `site-packages`.

It bit twice in one afternoon. First the container started cleanly and failed on the first
request. Then it took out roughly 200 CI tests with a `FileNotFoundError`. The fix is an explicit
call-time search order — `$HBA_PROFILE`, then beside the package, then the working directory —
and the container smoke test now calls `/profile` specifically, because `/health` would pass even
with an unreachable rulebook.

### CI was testing a copy of the code

Related, and worse. CI installed the package non-editable, and `pytest` (unlike
`python -m pytest`) does not add the working directory to `sys.path`. The suite was therefore
testing the installed copy in `site-packages`, not the commit under review. Every change would
have needed a reinstall to be tested at all — a very quiet way for CI to stop verifying anything.
Now it installs with `-e`.

### An explicit zero was rejected as missing

`parse_money` refused a value of `0`, so a property with an explicitly-stated $0 HOA was treated
as invalid input. Split into `parse_money` and `parse_optional_money`. Small, but the same theme
as the first bug: conflating "zero" with "unknown."

### A network guard blocked the test runner's own plumbing

The `no_network` conftest fixture blocked socket creation, which also blocked asyncio's internal
`AF_UNIX` socketpair — failing every web test with a message about network access that had
nothing to do with the actual cause. Now family-aware: `AF_INET`/`AF_INET6` blocked, `AF_UNIX`
allowed.

## The drift that had been hiding all day

The last task was meant to be a five-minute check: confirm the published snapshot at
`spartanburg.pplx.app` matched the work.

It did not, and not because it was stale. `app.js` contained a **second, complete implementation
of the scoring rules**, hand-written in JavaScript, predating the engine. Nobody had looked at it
all day. [ADR 0007](../adr/0007-http-service-container-and-split-ci.md) had warned, in its own
words, that two implementations "drift until they disagree about the same house" — and then
counted three doors when there were four.

By the time it was measured, the two disagreed like this:

| Rule | The page said | The engine says |
|---|---|---|
| HOA above $100/mo | score 0, **PASS**, disqualifying | −25, still a candidate |
| Roof at 17 years | a note, no points | −25 |
| Roof at 22 years | a note, no points | −35 |
| HVAC at 14 years | a note, no points | −15 |
| HVAC at 19 years | a note, no points | −22 |
| WATCH floor | 50 | 45 |
| Facts unknown | scored as if the answer were good | capped below TAKE |

Two of those are opposite decisions on real houses:

- **606 Andre Ct** — roof 17, HVAC 14, 2.5 baths, living area not recorded by the county — read
  as a confident **TAKE** on the published page. The engine scores it **52 WATCH**. The page was
  recommending an inspection on a house carrying an estimated $13,500–$33,500 of near-term roof
  and HVAC work, because an aging system produced a sentence instead of a deduction.
- **A house with a $150/mo HOA and nothing else wrong** was rejected outright by the page —
  score 0, PASS. The engine scores it **75 TAKE**. The page was discarding good houses over a
  $50 overage, which is the specific call the HOA rule had been changed to stop making.

Neither is a coding error. The page was correct when it shipped; the profile moved and the page
did not. That is what two hand-maintained copies of the same rules always do.

The browser cannot import Python, so it could not be given the same fix the API got. The rules
are now **compiled**: `tools/build_snapshot.py` reads `buyer_profile.toml` and writes a
declarative rule block into `data.json`, and `app.js` evaluates that block in the same order as
`analyzer/core/scoring.py` — hard fails, deductions, capital expenses, unknown-facts cap, then
verdict bands. Three things hold it:

1. `python tools/build_snapshot.py --check` fails CI when `data.json` goes stale.
2. Tests trace every threshold, weight, and dollar band back to the profile and to
   `analyzer/core/capex.py`.
3. A test asserts `app.js` actually reads `DATA.rules`, that the old hand-written branches are
   gone, and that no bare threshold has reappeared inside the scorer.

Check 3 is the load-bearing one. Checks 1 and 2 would both have passed on the broken version —
correct data sitting beside a function that ignores it is indistinguishable from a working
system. Full reasoning in
[ADR 0008](../adr/0008-browser-rules-are-compiled-not-rewritten.md).

Verified by hand in a browser against `analyze()` on identical facts:

| Case | Engine | Page |
|---|---|---|
| 606 Andre Ct, size unknown | 52 WATCH | 52 WATCH |
| $150/mo HOA, nothing else wrong | 75 TAKE | 75 TAKE |
| All facts known, nothing failing | 100 TAKE | 100 TAKE |
| Roof 22, HVAC 19 — both overdue | 43 PASS | 43 PASS |
| 25-minute commute | hard fail | 0, deal-breaker |

The page also gained a "Run the full engine" section stating plainly what a snapshot can and
cannot do — it scores typed facts and looks nothing up — with the commands to run the CLI, the
batch runner, and the container.

## Decisions worth restating

- **An old house is a caveat, never a deduction.** Build year before 2000 produces a note. Age
  alone is a prompt to look closer, not evidence of a worse house.
- **Three hard fails only:** FEMA flood zone, well or septic, commute over 20 minutes. Everything
  else is survivable and scored.
- **Maintenance reserve reports three methods side by side and never averages them.** Averaging
  three guesses produces one confident-looking number that is worse than any of the three.
- **Broadband is labeled an estimate with an instruction to call the ISP.** FCC data is
  census-block precision; a neighbour's fiber is not your fiber.
- **The commute anchor is Spartanburg Medical Center with a 6:30–7:00am arrival window** — the
  hospital shift change, not generic office peak.
- **The public site stays a snapshot; the real tool is a local container.**
  [ADR 0001](../adr/0001-static-snapshot-plus-local-container.md).

## Later the same day — the hazard layer the roadmap actually asked for

Auditing the roadmap turned up a quiet substitution. Item 3 read "pull FEMA National Risk
Index for the tract." What got built was the **NFHL flood zone**, which is a different FEMA
product answering a different question: NFHL is the regulatory flood map that decides whether
a lender demands flood insurance, and the NRI is a modeled expected-annual-loss index across
18 hazards. Both are useful. Only one of them was asked for, and the limitations file was
still carrying an entry claiming the NRI endpoint was unreachable, which was no longer true.

### The endpoint, since the documented one is not the one that works

`hazards.fema.gov/nri/api/...` does not answer. The layer that does:

```
https://services.arcgis.com/XG15cJAlne2vxtgt/arcgis/rest/services/
  National_Risk_Index_Census_Tracts/FeatureServer/0/query
```

469 fields, census-tract resolution, no API key, data version December 2025. All 18 hazard
codes carry `_RISKS` (score), `_RISKR` (rating) and `_EALT` (total expected annual loss).

**The gotcha that cost a query:** `_EALB`, `_EALP` and `_EALA` are *not* present for every
hazard — drought has neither a building nor a population loss model. ArcGIS rejects the whole
request if any single requested field is unknown, so asking for a building-loss field on
drought's behalf 400s the entire hazard profile. Only suffixes that exist on all 18 are
requested. A live test now asks for all 54 field combinations at once, so the day FEMA renames
one, the test says which.

### Two findings that changed the design

**The rating labels are not a shared scale.** FEMA publishes five tidy labels per hazard, and
they map so naturally onto a deduction table that writing one feels like the intended use.
Sampling 2,000 California tracts off the live layer says otherwise — the bins are cut per
hazard, against that hazard's own distribution:

| Rating | Wildfire percentile | Composite percentile |
|---|---|---|
| Very Low | up to 68.5 | up to 20.1 |
| Relatively Moderate | 88.4 – 96.2 | 55.9 – 84.3 |

The tract containing **Paradise, California** — the town the 2018 Camp Fire destroyed —
returns wildfire percentile **95.2** with a wildfire rating of **"Relatively Moderate"**. A
deduction table keyed on that label charges Paradise the mid-tier penalty. Worse, the same
tract's all-hazard **composite** reads **32.3** and rates "Relatively Low", because the
composite averages all 18 hazards and 15 of them do not apply in Butte County. Any headline
composite number describes Paradise as a low-risk place to live.

So: percentiles are the value, labels survive only as a note, and the composite is printed
only when it understates a genuinely elevated hazard — and then only to say so out loud.

The sample was ordered by object ID rather than randomly, which is enough to prove the bins
differ per hazard and **not** enough to publish national cut points. Both readings point the
same way: do not build points on top of the labels.

**A zero is not good news.** 900 of those 2,000 tracts return a wildfire score of exactly
`0.0` with rating `"No Rating"` — FEMA declining to model the hazard, not FEMA reporting its
absence. This is the same bug class as the parcel station this morning, where silence scored
as perfection. In a deduction system it fails in a specific and nasty way: not-modeled reads
as 0, 0 is below every threshold, and the house gets silently *credited* for a hazard nobody
measured. Sentinels are now caught and reported as `unavailable` with the note that unknown is
not the same as low.

### Reporting, not scoring

The station provides exactly one fact, `hazard_profile`, and `PropertyFacts` has no field by
that name. The hazard data travels on the analysis document for a human to read and is
structurally invisible to the engine. Reasoning is in
[ADR 0009](../adr/0009-hazard-risk-is-a-caveat.md); the short version is that a tract spans
several square miles, the tool cannot tell the ridge from the draw, and the financial
consequence of hazard exposure is already priced by someone whose job that is. The correct
output is not a guessed penalty, it is "go get a quote."

Verified rather than asserted: the same address scores **74 / WATCH with byte-identical
deductions** whether the risk station runs or not.

### A test caught a design bug, not a typo

`test_every_station_declares_what_it_provides` failed immediately — it asserts every fact a
station provides lands on `PropertyFacts`, which is exactly the invariant the new station
breaks on purpose. Loosening it would have thrown away a real guard. Instead there is now an
explicit `REPORTING_ONLY_FACTS` allowlist with the reasoning written next to the entry, plus a
second test asserting nothing in that list is *also* a scoring input. Adding to the list is a
design decision that has to be justified in a comment, not a way around the check.

The composite footnote also shipped with a real bug, found by a test written to assert it
stayed quiet for Spartanburg. The first version fired on any 25-point gap between the
composite and the worst hazard. Spartanburg's composite is 18.6 and its worst hazard is hail
at 51.7 — a 33-point gap and nothing anyone needs to act on. The note now also requires the
hidden hazard to be at or above the 75th percentile. Noise in a caveat channel teaches people
to skip the caveats.

### The California seam

A friend needs this for California, so the hazard list moved into `buyer_profile.toml` rather
than the code:

```toml
[risk]
hazards           = ["SWND", "TRND", "HAIL", "WNTW", "HWAV", "DRGT", "WFIR"]
caveat_percentile = 90.0
```

California swaps that line for `["WFIR", "ERQK", "DRGT", "HWAV", "LNDS"]` and changes nothing
else, because the NRI is a national dataset and the parsing is hazard-agnostic. Codes are
validated at construction, so a typo fails loudly instead of silently dropping a hazard. The
`[risk]` table is optional and defaults to reporting nothing, so a profile written before
today still loads.

Fixtures for **both** a South Carolina and a California tract are committed. A station tested
only against Spartanburg passes whether it reads percentiles or labels, because in Spartanburg
the two agree. Paradise is the fixture that can tell them apart, which is why it is in the
repo even though nobody is buying a house there.

## Still later the same day — parity, then the question read backwards

Two items, and they turned out to be the same item twice: something existed on one door and not another.

### The page had no hazard data, so I gave it two shapes

The CLI and the API had been reporting the National Risk Index for hours. The published page did not know it existed. That is not a missing feature, it is a **disagreement about reality between two doors on the same engine**, which is the failure ADR 0008 exists to prevent.

Building it raised a question the CLI never had to answer: *which tract?* The CLI gets an address, so it gets a tract. The page has 18 ZIP polygons and no address. So the snapshot ships hazard data in **two shapes on purpose**:

| Shape | Answers | Resolution |
|---|---|---|
| County min / median / max across 87 tracts | "Is wildfire a thing here at all?" | Whole county |
| Per-ZIP **centroid** tract | "What about where I'm actually looking?" | One tract, not a ZIP average |

They disagree, and the page says so rather than picking a winner.

The county query is one request: `STATEABBRV='SC' AND COUNTY='Spartanburg'` returns all **87 tracts** with no transfer-limit overflow, so the whole distribution is a build-time fetch rather than 87 of them.

### What the county distribution actually says

| Hazard | min | median | max |
|---|---|---|---|
| Wildfire | 22.3 | 59.7 | 82.4 |
| Hail | 35.4 | 63.0 | 81.1 |
| Tornado | 30.5 | 52.1 | 77.3 |
| Strong wind | 19.0 | 46.9 | 76.2 |
| Winter weather | 20.2 | 33.8 | 51.2 |
| Heat wave | 5.8 | 26.0 | 57.5 |
| **Drought** | **71.0** | **86.5** | **94.7** | *(modeled in only 20 of 87 tracts)* |

Drought is the **highest-percentile hazard in the county where it is measured at all**, and at 606 Andre Ct it reports "not modeled". That is the abstract "a zero is not good news" argument from ADR 0009 with local numbers attached, and it is now a test: `test_where_drought_is_modeled_it_is_high` fails if a future NRI release makes that copy false.

### Community resilience is a county figure wearing a tract's clothes

Verified across four counties before deciding how to label it:

| County | Tracts | Distinct resilience values |
|---|---|---|
| Spartanburg SC | 87 | **1** (44.5694) |
| Greenville SC | 123 | **1** (43.8739) |
| Butte CA | 54 | **1** (48.2715) |
| Cumberland NC | 81 | **1** (22.4215) |

Social vulnerability, by contrast, takes **74 distinct values across Spartanburg's 87 tracts**. So resilience is published per county and joined onto the tract table, and presenting it as a neighbourhood signal would be an invention.

Rather than hard-code that, the builder computes `varies_by_tract` from the data and the label follows automatically. If FEMA starts publishing it per tract, the page stops calling it a county figure without anyone editing a string.

### The label problem, in one ZIP

ZIP 29301 centroid tract `45083021902`: hail **71.0 "Relatively Moderate"**, wildfire **68.9 "Relatively Low"**. Two percentiles two points apart, two different labels — the ADR 0009 argument reproduced inside a single ZIP. Which is why the bars sort **worst-percentile-first and never by label**: sorting by label puts hail above wildfire, the exact inversion the callout warns about.

And 606 Andre Ct sits in that same ZIP, in tract `45083020601`, with wildfire **28.4** against the centroid's **68.9**. A **40-point intra-ZIP spread**, which is the whole argument for why the centroid figure is labelled a sample and not an average.

### The question every door was answering backwards

Everything so far answered: *given this house at this price, can I afford it?* Nobody shopping asks that first. They ask **what is the highest number I can type into the price filter**, and no door answered it.

`solve_max_price` does. It is bisection over the real `cost.compute`, not an algebraic inverse — [ADR 0010](../adr/0010-inverse-affordability-is-two-answers.md) has the reasoning, and it comes down to the deed fee stepping per $500 and the assessment-ratio branch. A closed form would restate all of that and then go stale silently. Bisecting `compute` cannot disagree with `compute`, because it is `compute`.

It returns **two prices**, always:

| At a 22% front-end DTI cap | Price | Basis |
|---|---|---|
| Lender | **$1,046,433** | PITI only — what a pre-approval shows |
| Household | **$894,622** | PITI + the conservative edge of the maintenance reserve |

A **$151,811** gap. Reporting only the first is accurate and misleading.

Two details that are not incidental. The bisection returns the **low** edge of the bracket, because rounding a max price up hands back a number that breaches the ceiling — the one direction of error that costs money. And the **mortgage-insurance warning is attached to the answer, not the input**: the down payment is fixed while the solved price moves, so a higher answer is mechanically a lower down-payment percentage. At $80,000 down, the 22% answer is 7.6% down. MI is modeled nowhere in this project, so the figure is explicitly an upper bound.

At a 0.8% ceiling it reports **infeasible** and names the cause: even at $80,000 with no loan at all, taxes and insurance put DTI at 1.0%. Fixed costs are the constraint, so a cheaper house does not solve it. Returning `0` there would have implied it does.

### The finding I did not expect from a solver

Working target: **$310,000**. Lender ceiling at the profile's own DTI target: **$1,046,433**.

**DTI is not the binding constraint at this income, and it never was.** Cash to close and the appraisal are. The forward calculator could not surface that, because it only ever answered about one price at a time.

### The parity test paid for itself in one run

The page needed its own solver — a bisection is behaviour, not a rule table, so there is nothing for the ADR 0008 compiler to compile. `pitiParts` was extracted out of the existing KPI block so the page's two readings of PITI are one function rather than a copy, and `solveMaxPrice` bisects over it.

Then `TestTheTwoDoorsAgree` shells out to `node`, runs the browser solver against the same profile, and asserts both land within $2 across three ceilings.

It failed immediately. Python floored the search at the down payment; JavaScript bracketed from zero and cheerfully returned a max price of **$13,379 against an $80,000 down payment**. Both sides returned a confident number and only one was right — precisely the failure a second implementation introduces and only a parity test catches. Fixed in `app.js`, and the guard is now its own test.

### Two assertions worth pointing at

`test_only_the_hazard_renderers_touch_the_hazard_block` walks every `DATA.hazards` reference in `app.js` and asserts the enclosing function is one of two names. If someone wires hazard data into the scorer later, that test makes them go write an ADR about it first.

## Phase 3 — the thing that remembers

Everything up to here was stateless. You type an address, the engine hands back a document, and
nothing recalls the conversation happened. Fine for arithmetic, wrong for the actual job, which
runs for about a year: which houses are still live, what did this one cost in March, what did we
assume about the roof and was it true.

### Why it is a separate package and not a module in the engine

ADR 0002 says the core does no I/O. ADR 0007 says the CLI, batch runner, HTTP service, and static
page are thin doors on one engine. Storage is I/O. Put a database call inside the engine and both
of those stop being properties and become marketing copy.

So `ledger/` is a top-level package and `analyzer/` does not import it. The doors wire them
together: `analyzer/cli.py --save` imports it *inside the branch*, so the stdlib-only install path
never touches it. A test reads the engine's own source and asserts the import is not there,
because a purity claim nobody checks is a comment.

### Why it is append-only, and why that is enforced by SQLite and not by me

The same house scored 74 in March and 68 in June. Neither number is wrong. A schema with an
`updated_at` column answers "what did this score in March" with June's number, and does it
silently.

Worse, a score can move for three unrelated reasons: the price changed (a fact about the market),
the engine changed (a fact about our code), or the profile changed (a fact about us). Overwriting
destroys the ability to tell those apart, which is the only reason to keep history at all. So
every analysis stores `engine_version` and a `profile_fingerprint`, and `diff()` returns
`comparable: false` with a reason when either differs. The price delta is still reported in that
case -- a price is a fact about the world and does not care which version of our code saw it.

`RAISE(ABORT)` triggers on UPDATE and DELETE for `analyses` and `journal`. Not `RAISE(IGNORE)`,
which would swallow the write and report success. Not application-level convention, because the
guarantee has to hold for `sqlite3 ledger.db` at a shell prompt. There is now a CI step that opens
the file with a plain `sqlite3` connection, no ledger import at all, tries an UPDATE, and fails the
build if it succeeds. That is the difference between a guarantee and a habit.

### The trigger bug that taught me something about cascades

The DELETE trigger on `analyses` blocked every delete, which is what it is for -- and it also
blocked `ON DELETE CASCADE`, so no property could ever be removed. Including one created by a
typo. The fix is a guard: the trigger only aborts while the parent property still exists.

```sql
WHEN (SELECT COUNT(*) FROM properties WHERE key = OLD.property_key) > 0
```

A cascade is a delete, and a blanket "no deletes" rule catches your own cleanup.

### Identity, and the parser I did not write

Normalization is upper-case, strip punctuation, collapse whitespace. That is all. The canonical
form comes from the geocoder's `matched_address`.

I wanted an address parser. The reason not to: a partial parser fails by silently merging two
different houses on one street, and that failure is invisible in the output. No parser fails by
showing the same house twice, which you notice in about a second. Pick the loud failure.

When geocoding degrades the key gets an `unresolved:` prefix, so a guess can never collide with a
resolved address. That leaves no merge path -- append-only means rows cannot be re-pointed -- so
the remedy is to re-analyze once geocoding works and delete the stub while it is still a typo.
Written down in KNOWN_LIMITATIONS rather than papered over.

### A journal, not a notes field

Entries have a `kind` (assumption, decision, observation, outcome, status) and an optional
`resolves` pointing at an earlier entry. An outcome closes the assumption it settles, and
`open_assumptions()` lists every claim nothing has checked. That is the difference between a
decision journal and a scratchpad: it can tell you what you believed and never verified.

One bug worth remembering. The open-assumptions query is:

```sql
id NOT IN (SELECT resolves FROM journal WHERE resolves IS NOT NULL)
```

Without that `WHERE`, a single NULL in the subquery makes `NOT IN` return unknown for every row and
the result set is empty. SQL three-valued logic, doing exactly what it promises.

Status is the only mutable column in the only mutable table, and every status change writes a
journal entry in the same transaction. There is no state where the status moved and the reason
does not exist.

### `forget` refuses, on purpose

Once a property has more than one analysis or any non-status journal entry, `forget` says no. It
exists to delete a typo, not a decision. A house you rejected is data; `passed` and `archived` are
the answers.

### Two bugs the tests did not catch, and one dry run did

The suite went green on the first proper run after fixing the test double -- I had used a
duck-typed stand-in for the profile where production passes a frozen dataclass, so the fingerprint
went down a code path nothing real uses. Made it a real dataclass.

Then I dry-ran the new CI steps locally instead of pushing and watching, and both failed
immediately:

1. `ledger.cli stats --json` was a parse error. `--json` was declared only before the subcommand,
   and `stats --json` is what a person actually types. Fixed by giving every subparser a copy via
   a parent parser -- with `default=argparse.SUPPRESS`, which is the whole trick. Without it the
   subparser's own default overwrites a value already parsed from before the subcommand, so
   `--json stats` would silently print human output to a script that asked for JSON.
2. `ledger` was missing from `[tool.setuptools.packages.find]`. CI installs the project and runs
   bare `pytest`, which does not put the working directory on `sys.path`. It imported fine here
   and would have failed in CI with `ModuleNotFoundError` -- the identical shape of the bug the
   `tools/` scripts caused earlier today.

Running the CI step on my own machine cost two minutes and caught two things.

## Phase 4 item 1 — the amortization schedule, and why a twelve-line loop took a day

The roadmap called this an "amortization calculator" and I had been treating it as almost done, because `cost.monthly_payment` already returns the level payment. Striking through half that line this morning is what made me actually look at the gap.

The payment is one number. The schedule is the four numbers that change behaviour:

- The payment on the target loan is $1,151.49, and $995 of the first one is interest.
- Principal does not exceed interest until payment 236. Year 19.7 of a 30-year note.
- $200 extra a month ends it 9 years 11 months early.
- That $200 saves $89,642.

I could not have guessed the crossover month within five years. That is the number I want in front of me before I sign anything.

### Integer cents, because 360 sequential operations is a lot of float

The loop is not one calculation, it is 360 of them feeding each other. I have written this kind of thing before and gotten a final balance of `-0.004`, which is the sort of output that makes a reader stop trusting the whole column.

So the running balance is an `int` count of cents and floats only appear at the boundary when the dataclasses get built. There is nothing to accumulate error in.

The rounding is `Decimal` with `ROUND_HALF_UP`, not Python's `round()`. Python does banker's rounding — `round(0.125, 2)` is `0.12` and a servicer rounds it to `0.13`. One cent a month is 360 cents, which is enough to disagree with a real amortization notice, and being able to hold this table next to a lender's paperwork is most of why it exists.

### The 361st payment

First run of the finished loop, six test cases, and every single one came back with `months_to_payoff` one higher than the term. A 30-year note with 361 payments, the last one for $3.31.

Obvious once seen: the level payment is rounded to the cent, so 360 of them do not land exactly on zero. Real notes handle it from the other end — the last scheduled payment is whatever clears the loan, $1,374.78 instead of $1,371.49.

What I want to remember is that this was not a rounding error, it was a whole extra row. A tolerance check on the final balance would have passed. `test_payoff_takes_exactly_the_term` is parameterized across six loans, including a 0% one and a twelve-month one at 30%, and it caught it in all six.

### Two guards that are about failing fast, not about mortgages

`MAX_MONTHS = 1200` is not a business rule. It is a stop, because an unbounded `while balance > 0` reachable from an HTTP endpoint is an outage rather than a bug.

And if the payment does not cover the month's interest, the balance grows forever. That raises immediately with both numbers in the message instead of spinning 1,200 times first.

The third guard is the one I am most glad about: `annual_rate > 1` raises. `schedule(loan, 6.67, 360)` would otherwise return a complete, internally consistent, entirely confident schedule at 667%. A wrong answer that satisfies all of its own invariants is the dangerous kind, and this project has been bitten by that shape before — the geocoder substitution last night was exactly the same failure, a perfect analysis of the wrong thing.

### Saying loudly that this is not PITI

The schedule says $1,151.49. `cost.compute` says $1,652 for the same house. Both correct, about different questions, printed within a few inches of each other.

A docstring is not enough for that. So `excludes` is in the payload, the CLI header says "principal and interest only", the CLI footer repeats the list, the HTTP `note` names PITI, and a test asserts the list has exactly four entries so nobody can quietly trim a caveat.

Mortgage insurance is on that list and is still modeled nowhere in this project. A schedule is the obvious place to add PMI drop-off — the LTV at every month is sitting right there in the balance column — and I did not build it. Third document now where that gap is written down instead of glossed.

### Two tests I wrote badly

Both renderer tests failed on the first run and neither was a code bug.

The first parsed year numbers out of terminal output without stripping the ANSI colour codes, so it found nothing and asserted an empty list against seven values. A test that cannot read its own subject is worse than no test.

The second asserted "(1 payment)" singular on a loan whose final year has two payments. I had copied the expectation from a different loan amount in an earlier manual run. Now the singular case has its own test with an assertion that the fixture still exercises that branch, so it fails loudly if the loan amount ever changes rather than silently testing nothing.

### Where it landed

`analyzer/core/amortization.py`, pure, no I/O, no network. Two doors: `--amortize` and `--extra-monthly` on the CLI, and `POST /amortization` where every field is optional and defaults to the profile's own loan. Rate is a percentage over HTTP to match `dti_pct` on `/max-price`, and the core rejects fractions above 1 as a backstop.

The CLI prints seven rows — year 1, every fifth, and the payoff year — because thirty rows in a terminal is a wall nobody reads. The full 360 are in `--json` and behind `include_payments` over HTTP, defaulting off since they are about 40 KB.

### Still unfinished here

The static page has no amortization view. Same gap as the ledger, and the same rule applies: under ADR 0008 a browser version has to be compiled from this module, not hand-ported, or it becomes a second implementation like `solveMaxPrice` already is.

Extra payments are monthly only and assumed to start at payment 1 and never stop. Real prepayment is a tax refund in April and nothing for two years. `interest_saved` is a ceiling, not a forecast.

No recast, no refinance, no ARM, no escrow change. Thirty years of identical payments is what a schedule is, and anything that changes the terms starts a new one.

## The schedule reaches the page, and the refactor that broke a test

The schedule shipped this morning with two doors, neither of which is a browser. The best
output this project produces — the month where a payment stops being mostly interest — needed
a terminal to see. So it went on the page.

### Why this is a hand-port and not a compiled table

[ADR 0008](../adr/0008-browser-rules-are-compiled-not-rewritten.md) forbids rewriting rules in
the browser: scoring is computed in Python and compiled into `data.json`. A schedule does not
fit that. It is not a table of rule outputs, it is a loop whose inputs are three slider
positions, and precomputing it means compiling a schedule per combination of price, down
payment, rate and extra payment. There is nothing to compile.

So `app.js` got its own `amortize()`, which is a second implementation of arithmetic that
already exists — exactly the thing ADR 0008 exists to prevent. The rule ADR 0008 actually
encodes is *no unaudited second implementation*, and `solveMaxPrice` already set the precedent:
a solver in the browser, checked against Python under `node`. Reasoning is in
[ADR 0013](../adr/0013-the-page-gets-its-own-schedule-under-a-parity-test.md).

### The tolerance is zero

`tests/test_amortization_parity.py` compares all 360 rows — interest, principal, extra, closing
balance — plus the annual rollup, plus the six headline figures, across nine parameter sets.
Zero tolerance. Not a dollar, not a percent, to the cent.

That is only defensible because both sides do the same arithmetic deliberately. Money is
integer cents on both. Python rounds with `Decimal` and `ROUND_HALF_UP`; JavaScript's
`Math.round` is half-up for positives and money here is always positive, so they agree by
construction rather than by luck. The final payment is balance-plus-interest on both, so the
browser cannot reintroduce this morning's 361st payment.

A loose tolerance would hide the exact bug the file is for. Both implementations return a
complete, confident, internally consistent schedule. Nothing on the page looks wrong. Only one
is right.

It matched on the first run — 360 rows, nine cases, zero drift, including a 0% rate, a 15-year
term, a 30%-APR twelve-month loan, and 6.00% where a half-cent genuinely occurs.

### The refactor that broke `test_max_price.py`

`pitiParts` had the payment formula inline. The schedule needs the same formula and a second
copy in the same file is indefensible, so it moved into `pmt()`.

That broke the max-price parity test. Its harness pulls `pitiParts` and `solveMaxPrice` out of
`app.js` by regex and evals them under `node`; `pitiParts` now called a function the harness
never loaded, and five tests failed on the first full-suite run. Fix was one extra `eval`.

Worth recording because the harness is brittle by design and the brittleness did its job: a
refactor reached into code the browser shares, and a test written for a different reason caught
it immediately.

### A theme bug found by fixing it

Rebuilding the two new charts on theme toggle instead of calling `.update()` revealed why the
existing two keep dark gridlines in light mode: Chart.js copies axis and legend colours into its
options at construction, so `.update()` re-renders with the old theme's greys. The amortization
charts re-read the CSS variables. The other two were left alone this pass and the inconsistency
is now in `KNOWN_LIMITATIONS.md` rather than sitting unnoticed.

### Three things the browser QA caught

1. **A blank x-axis.** The tick callback labelled only multiples of 60, and Chart.js with
   `maxTicksLimit: 7` never picks one — so both charts showed nothing but "1". Converting
   whatever tick it does pick fixed it. Then `Math.round(1/12)` labelled the first payment
   "yr 0", so it is `Math.ceil` now: payment 60 is the last payment of year 5.
2. **Subscript glyphs in the formula line.** `interest₁ = balance × rate/12` rendered as
   near-illegible specks in the mono face. Plain words instead.
3. **A clipped balance column at 375px.** Five money columns do not fit at the table's default
   10px cell padding. The wrapper scrolls horizontally, but a table you have to swipe to reach
   the balance in is a table nobody reads. Tightened cells under 560px fit all five.

### What the page says out loud

The schedule reports $1,477 and the affordability section above it reports $2,024 for the same
house. Both correct about different questions, and a person reading quickly will take the
smaller one as their monthly cost.

So the section states the excluded four — tax, insurance, HOA, mortgage insurance — names the
PITI figure from the section above, and prints the difference as a dollar amount rather than
leaving it to be inferred. The prepayment callout also says plainly that extra principal does
not shrink the escrow half, so the monthly outlay does not fall until the loan is gone.

## Phase 2 — the document extractor, and the discovery that the model was the easy part

[ADR 0004](../adr/0004-llm-scope-boundary.md) had drawn this boundary ten commits earlier: the
model reads, the code decides. Extraction from documents, a citation for every field, a human
confirmation before anything counts, and never a dollar figure or a score.

Then it sat there as prose. Building it revealed the part the ADR states but does not settle:
**what stops the boundary from being crossed?**

### The response that is dangerous is the one that looks fine

Calling a model is fifteen lines of `urllib`. Deciding what to do with the answer took the day.

The failure mode worth designing against is not garbage — `json.loads` catches garbage. It is
this:

```json
{"field": "estimated_value", "value": 312000, "quote": "Year built: 1998."}
{"field": "roof_age_years",  "value": 12,     "quote": "The roof was replaced in 2014."}
```

Both parse. Both look like output. The first is a confident dollar figure ADR 0004 forbids
outright. The second is a plausible number attached to a sentence that is not in the document.

If the code accepts either, the boundary was decorative and the person clicking "confirm" is
being asked to catch what the system did not.

So `core/extraction.py` accepts a field only when four things hold — **declared, permitted,
grounded, plausible** — and each failure is recorded with its reason rather than dropped. That is
[ADR 0014](../adr/0014-extraction-is-refused-by-default-and-grounded-in-a-quote.md).

The load-bearing one is **grounded**: the quote must appear in the text that was sent. Not
similar to it — in it. Whitespace is normalised, because `pdftotext` wraps at 80 columns and a
sentence quoted across a line break is absent character-for-character while being obviously
present to a human. Nothing else is relaxed. A quote matching at 85% is a quote the model partly
wrote itself, which is the case the check exists for.

And it is checked against the **redacted** text, not the original file. Grounding against the
original would happily accept a quote containing a phone number the model never saw — the check
would keep passing while no longer testing anything.

A hostile-response demo confirmed all six refusal paths, including a fabricated `year_built: 1998`
that was *correct* and still refused, because its quote was invented. Being right by luck does not
get through.

### Redaction became a type, because a boolean is a promise nobody keeps

`THREAT_MODEL.md` had promised redaction that "cannot be skipped by a caller". A `redact=False`
parameter cannot deliver that. Some call site under deadline pressure sets it and nothing fails.

So `redact()` is the only constructor of `RedactedText`, and the send path in `extract/run.py`
hands the provider `redacted.text` — it never sees the `Document`. Python has no private
constructors, so this is not impossible; it is impossible *by accident*, and loud in a diff. A
test fails if `redact()` ever grows a `skip=` or `unsafe=` parameter.

It lives in `core/`, which by ADR 0002 cannot import anything that reaches a network. That is
what makes it structural rather than conventional: there is no arrangement of core code where
document text reaches a model without passing through it.

The order of operations in `run.py` *is* the security property, and it is written down as such:
**load → filter pages → redact → send → judge → log.**

Two honest limits went straight into `KNOWN_LIMITATIONS.md`. Free-standing names are not detected,
because a detector good enough to catch "Brown" also destroys "brown water staining below the
window" — and a redactor that quietly mangles the sentences a model must read produces
confidently wrong extractions. And any run of eight or more bare digits is removed as a possible
account number, which over-redacts a parcel ID written without separators. Over-redaction was
chosen deliberately: a lost parcel number is something the county station already provides, and
an account number reaching a third party is not recoverable.

### A provider that is not a model, so that all of this has tests

CI has no credentials and should never have any. A feature only observable by spending money at a
third party has no test suite.

So there are three providers behind one interface — Ollama, any OpenAI-compatible endpoint, and
`OfflineProvider`: about twenty regexes whose docstring says in its first line that it is not a
language model and does not pretend to be. It is the **default at every door**, which matters most
at `POST /extract`, an endpoint that accepts a file from whoever can reach the port. A cloud
default would turn one exposed container into an exfiltration path without anyone choosing that.

Its quotes are real spans from the document, so it faces the same grounding check as any model.
Nothing gets a pass for being local.

The payoff is that grounding, coercion, bounds, forbidden fields, the call log, and both doors are
all covered offline — and a fresh clone gets a working demo instead of a key prompt.

### The log that must not know what it logged

`llm_calls.jsonl` records timestamp, document hash, provider, fields requested, refusal reasons,
and whether redaction fired. It stores **no document text and no extracted values**.

That is not an oversight to fix later. A log holding what it sent would be a second copy of the
sensitive material with a longer retention than the request that created it — the audit trail
would become the largest data-at-rest risk in the project. A test asserts the log file does not
contain "vapor barrier", "architectural", or either name from the fixture.

The hash is of the text **as sent**, post-redaction, so two runs redacting different names are
distinguishable — visible immediately in the demo, where the same file logged `9005dbd8` with
`--name` and `a9658224` without.

`write_record()` swallows `OSError` on purpose. Observability must not break the thing it
observes, and losing an extraction because an audit line could not be appended is the worse
outcome. The mitigation is that the CLI prints the log path every run, so a log that has stopped
growing is visible. That trade is written down rather than assumed.

The acceptance rate from `extract stats` is the number that makes a provider swap measurable: a
model that starts fabricating shows up as a rise in `citation not found`, not as wrong numbers in
front of a buyer.

### Four bugs, three of them mine and one of them the test's

1. **The HOA dues pattern could not cross a full stop.** Anchored on `hoa|association` with a
   `[^.\n]` class, it could not reach "Dues of $85.00" in "governed by an HOA. Dues of $85.00".
   Re-anchored on `dues|assessment|fee`.
2. **`defects` returned a wrapped fragment** — "based on the seller's statement and observed
   granule loss" — because the first line containing "recommend" is mid-narrative in an 80-column
   report. Two passes now, bulleted lines first.
3. **The fixture itself was ambiguous**: "$85.00 per month are payable quarterly" made
   `hoa_dues_period` genuinely undecidable, so the demo was wrong for an honest reason. Reworded.
4. **A test was wrong, not the code.** `test_every_schema_field_could_plausibly_be_located_by_a_page_keyword`
   failed on `known_flooding_mentioned` and `defects`, but "flood" plainly does cover "flooding" —
   the test's stem heuristic was too strict. Rewritten to match stems in both directions. Worth
   naming because the reflex is to change the code until the test passes, and here that would have
   widened the keyword list to satisfy a broken assertion.

### Two doors, no new logic

`python -m analyzer.extract.cli` gets `read`, `log`, and `stats`, following the `ledger.cli`
precedent. `read` prints **the quote under every value**, because confirming a field without
reading the sentence it came from is rubber-stamping — and a rubber-stamped confirmation is worse
than none, since it launders an extraction into something a score would treat as reviewed. Every
run ends with the line that nothing here has affected a score.

Over HTTP: `POST /extract`, plus `GET /extract/schema` and `GET /extract/log`. The schema endpoint
publishes the 18 forbidden fields alongside the 16 declared ones, which describes a boundary
better than prose about one does. Uploads are written to a temp file and deleted in a `finally`,
so a document does not outlive the request even if extraction raises. A provider failure is a 200
with `error` set, matching the degradation rule at the top of `service/app.py` — the caller still
gets the redaction report and the record of what was sent.

`--all-pages` is opt-in, and the asymmetry is the point: redaction narrows and has no escape
hatch, while the page filter widens, so widening is an explicit decision recorded in the command
someone typed.

### What is deliberately not finished

A confirmed finding still cannot reach a score. `Finding.to_value()` exists and raises until
confirmed, but nothing stores a confirmation — that needs a ledger table and a UI. Building the
refusal machinery first means the boundary is enforced before anything depends on its output.

And the schema is one value per field, so a document listing nine deficiencies yields one. Recorded
as a limitation rather than fixed by loosening the schema.

**836 passed, 10 deselected. Was 712.** All of it offline, no key, no network.

## Weekly FRED MORTGAGE30US snapshot — rates

I added the non-fatal, location-independent `rates` station and a committed
`data/mortgage30us.json` baseline for Freddie Mac's weekly 30-year fixed average through
FRED. I tested the public graph CSV in this environment: it returned a parseable
`observation_date,MORTGAGE30US` body with `.` as its missing-value marker, and the current
latest observation was 2026-08-13 at 6.67%.

I did not call the graph CSV a supported API. The collector prefers FRED's documented
observations endpoint when `FRED_API_KEY` is configured, falls back to the keyless CSV, and
records which path answered. The `--check` command validates shape, derived statistics, and
the ten-day stale warning without making CI depend on a network request. I also added a
Thursday 18:00 UTC workflow; that is safely after the ~10:00 ET PMMS release in both DST
and standard time.

The rate station is intentionally not in `analyzer.pipeline`: a national weekly baseline
does not depend on the property's coordinates and fetching it once per address would make
reports less reproducible. The future sensitivity module should consume the committed
snapshot instead.

## Rate sensitivity band — Phase 4 item 2

I added a pure `analyzer.core.sensitivity` engine, a standalone `python -m
analyzer.sensitivity_cli` door, and a static-page SVG band from 5.00% through 7.50%. The
engine puts each rate through the existing full-cost, payment, and max-price paths rather
than teaching a new module its own PITI or DTI math. It returns the lender and household
max prices as well as payment and term-interest deltas against a labeled baseline.

The CLI reads the locally committed `data/mortgage30us.json` only when it is present; on an
absent snapshot it keeps the profile rate and says that it is an assumption. I initially
considered placing that file read in the core, but it would have broken the pure-core
boundary for the convenience of one CLI default. The snapshot reader therefore lives in the
CLI adapter, where a malformed present file fails loudly instead of becoming a silent
fallback.

"Wait versus buy" is deliberately a two-scenario calculation, not a forecast. Given a rate
and price today plus a hypothetical later rate and price, it states the full-PITI and
lifetime-interest delta and solves the later price that restores today's PITI. The page
uses a disclosed +25 bp stress case, calls it a stress test, and does not imply that rates
will move that way.

The page has its own small loop because the static deployment cannot call Python. That is
an ADR-0008 duplication, so `tests/test_sensitivity_parity.py` evaluates the actual
JavaScript with node and compares all displayed cents plus the break-even result to Python
with zero tolerance. A cent of drift is not rounded away. The feature's limits — no
forecast, no lender quote, no PMI, and full-term-interest assumptions — are appended to
`KNOWN_LIMITATIONS.md` and recorded in ADR 0015.

## Parcel snapshot — county primary proved reachable; kept the artifact bounded

I checked the live Spartanburg County CAMA FeatureServer rather than preserving the old
unreachable-server story. It reports ArcGIS 11.5, allows paginated queries, and exposes
181,531 parcels. Its field names are different from the 2021 mirror, so I gave the parcel
station separate current and mirror field lists. Current county values are now measured;
the mirror stays estimated and blocking when it is the fallback.

I built a 35,171-row, 389 KB Parquet candidate index for Spartanburg residential parcels,
not all county parcels. The buyer profile only names Spartanburg and a hospital commute
anchor, and committing a full binary county snapshot every night would permanently enlarge
Git history. The builder is sequential and polite, resumes after completed pages, fails
honestly on schema/page errors, and does not rewrite the artifact when the retained rows
have not changed. I left school attendance zone out because neither the CAMA layer nor the
county GIS catalog gave me a verified attendance boundary.

## Market velocity metrics — published aggregate context, not listing data

I added a bounded `data/market_velocity.json` from the public [Redfin Data Center Market
Tracker](https://www.redfin.com/news/data-center/), rather than touching listing pages or an MLS
feed. The artifact covers Spartanburg County, a clearly labelled county-equivalent Spartanburg
market scope, and the 18 target ZIPs already represented in the static submarket map. It carries
the source URLs, Redfin attribution, the non-commercial/no-resale constraint, the latest source
period, and only 13 months per geography — enough to audit every requested comparison without
committing the multi-gigabyte raw archive.

The source publishes the complete decision-context set: median days on market, months of supply,
active inventory, new listings, price-cut share, and average sale-to-list ratio. The committed
snapshot currently reaches 2026-05-31. Current reported values are surfaced as `measured` with
their period; same-month year-over-year deltas and 3/6/12-month least-squares slopes are
`derived`. I deliberately do not call a month-over-month movement a trend. Seasonality is not
solved by a short slope, so the output names YoY as the comparable direction and calls short
slopes descriptive context.

The builder streams and filters the gzip TSVs in place, validates the actual Redfin schema, and
never writes an archive into the repository. It treats an upstream 500 or truncated file as an
honest skipped refresh rather than a failed scheduled workflow. The station reads only the
committed artifact, does not need coordinates, and degrades for a stale snapshot or a geography
outside its bounded county/ZIP set instead of borrowing a nearby value.

One source-schema trap was worth recording: `REGION_TYPE_ID` is a geography-*type* code (`5` for
county and `2` for ZIP in the observed files), not a county FIPS or ZIP identifier. Matching it
to `45083`/`29301` would have silently produced no rows or the wrong join. The builder matches
the published county label exactly and parses only the strict `Zip Code: 12345` region label.
ADR 0018 extends ADR 0003 with that aggregate-versus-listing boundary and the Redfin licence
constraint; the limitations file now says plainly that county/ZIP context is not street-level
negotiating evidence.

## Phase 4 wiring — integration pass

I wired the rate snapshot, market-velocity snapshot, and pure sensitivity scenarios into the
service, added their HTTP failure coverage, and registered `market_velocity` as reporting-only
in the purity guard. I deliberately did **not** add `MarketVelocityStation` to the default
per-property pipeline: it would read the committed snapshot on every analysis without producing
`PropertyFacts` or affecting the score. The explicit `/market-velocity` route remains the honest
reporting door instead.

I added the profile-owned target ZIP list, regenerated the velocity artifact so its provenance
names that block, and added offline checks for all three new snapshot builders to CI. I also added
the optional Arrow extra for parcel artifact work and the four Phase 4 ADR index rows. Both the
ordinary and node-required offline suites passed 897 tests with 13 live tests deselected, and all
three snapshot checks passed. I then called each new endpoint locally; the captured responses
showed 200 for the three valid requests and a 422 for the deliberately incomplete sensitivity
scenario.
